Be extremely concise. Sacrifice grammar for the sake of concision.
## Language conventions
- Write code reviews, PR descriptions, tickets, QA guides and admin messages in Russian unless told otherwise.
- Keep PR titles, commit messages and code comments in English.
## Code review format
When asked for a code review of the branch:
- Diff against master (`git diff master...HEAD`) and exclude autogenerated files (e.g. generated tdlib files).
- Number every finding and tag it P1/P2/P3 so I can say 'fix #2 and #5'.
- For each finding, state whether it is a real issue and how likely it is to happen.
- Never recommend fixing something you just called unrealistic. Keep the verdict and the recommendation consistent.
- Don't fix anything until I pick which items to fix.
## Fix and commit workflow
- Write a failing test first, then fix the code.
- Before saying a fix is done, run the checks for the affected project:
  - Elixir: `mix test`, `mix credo --strict`, `mix format --check-formatted`
  - Rails: `bundle exec rspec <related specs>` and `rubocop`
- When committing, stage only the files related to the task. Never use `git add -A`.
- Don't push or open a PR unless I ask.
- If changes span pushsms_api and Rails or the frontend, say whether they must be deployed together.
## PR descriptions
- Write PR descriptions in Russian.
- Save them to /tmp/<TICKET>-pr.md.
- If a file with that name already exists for another PR, use a new filename instead of overwriting it.
- Include test evidence (the spec run and its result).
- Exclude autogenerated files from the diff summary.
## Simplicity & diagnostics
- Prefer the simplest fix. If the solution needs Lua scripts, new infrastructure or extra moving parts, explain why a simpler option won't work before you build it.
- Before giving console, SQL or Loki snippets, check the real column names, registry names and ID types (session_id vs customer_id) in the code or schema.
- Don't ask me to hand-edit scripts. Give a complete corrected version instead.
- Check that YAML is valid (quote strings containing ': ') before suggesting .drone.yml changes.
- Model new infra (staging servers, CI) on the existing pushsms_api setup first.
